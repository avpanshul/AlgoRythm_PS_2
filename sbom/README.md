# SBOMs and release signing (Part D11)

## SBOMs

- `backend.cyclonedx.json` -- CycloneDX 1.6, generated from `backend/requirements.txt`:
  ```
  python -m cyclonedx_py requirements backend/requirements.txt -o sbom/backend.cyclonedx.json
  ```
- `frontend.cyclonedx.json` -- CycloneDX 1.5, generated from npm's own native command
  (reflects the full resolved dependency tree, not just direct deps):
  ```
  cd frontend && npm sbom --sbom-format cyclonedx > ../sbom/frontend.cyclonedx.json
  ```

Regenerate both after any dependency change -- an SBOM is a snapshot, not a
one-time artifact.

## Signing -- what was actually demonstrated

`cosign` was not available in the environment these were built in; `gpg`
was, so this demonstrates the same real property (a real key signs a real
artifact, verification passes on the genuine file and fails on a tampered
one) with GnuPG instead.

**A throwaway Ed25519 signing key was generated for this demonstration
only**:

```
pub   ed25519 2026-09-26 [SC] [expires: 2027-09-26]
      0F73 E191 3AAB 61AF BA14  1D45 33BD F145 4E67 9140
uid   ULPF Dev Release Signing (throwaway demo key) <release-signing@ulpf.local>
```

Its public key is `ulpf-dev-signing-key.asc` in this directory, for
reference only. **Its private key does not exist anywhere in this
repository** and was not persisted beyond the session that generated it --
a real release needs a real signing key with a real key-custody story
(see `docs/KEY_CEREMONY.md` for the same principle applied to the
checkpoint-signing key: generated once, documented who holds it, never
committed to version control).

Both SBOMs in this directory are signed with that throwaway key:
`backend.cyclonedx.json.asc`, `frontend.cyclonedx.json.asc` (detached
ASCII-armored signatures).

### Verified, live, in this session

```
$ gpg --verify sbom/backend.cyclonedx.json.asc sbom/backend.cyclonedx.json
gpg: Good signature from "ULPF Dev Release Signing (throwaway demo key) <release-signing@ulpf.local>" [ultimate]
```

Then, against a copy of the same file with a single byte appended (a stand-in
for any tampering):

```
$ gpg --verify sbom/backend.cyclonedx.json.asc /tmp/tampered.json
gpg: BAD signature from "ULPF Dev Release Signing (throwaway demo key) <release-signing@ulpf.local>" [ultimate]
$ echo $?
1
```

This is the real "flip a byte, detect it" property D11 asks for, proven the
same way this project already proved it for evidence bundles
(`docs/threat-model.md`) -- same principle, different artifact.

### For a real release

1. Generate a real signing key, held by whoever actually owns releases for
   this project -- not this throwaway one, and not generated by an AI
   session.
2. `gpg --armor --detach-sign` the SBOMs and the offline install bundle
   (Part D11 also asks for a signed offline bundle -- not built this pass;
   this SBOM signing is the demonstrated primitive it would reuse).
3. Publish the real public key somewhere independent of this repository
   (a keyserver, your organization's own trust anchor) so "verify against
   the key in the repo" isn't circular.
4. Anyone verifying: `gpg --verify <file>.asc <file>` against the real
   published key, exactly as demonstrated above against the throwaway one.
